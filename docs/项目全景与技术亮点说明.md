## 一、30 秒看懂这个项目

### 1.1 一句话定义

> 一家卖 AI 解决方案的公司（模拟企业"智联AI科技有限公司"），
> 需要一个能管住 **"客户怎么来 → 商机怎么推 → 需求怎么调研 → 成交怎么交出去"** 的销售管理系统。
> 通用 CRM 装不下 AI 行业的销售流程，所以基于成熟开源 CRM 做了一套**业务贴合型二次开发**。

### 2.2 核心技术壁垒：SuiteCRM 扩展机制

这是本项目**最值得讲的技术点**——它决定了"能不能改得动一个 20 年历史的开源企业系统，又不破坏它"。

| 扩展机制 | 作用 | 本项目用法 | 落地位置 |
|---|---|---|---|
| **Vardefs（字段定义）** | 无侵入新增/覆盖数据字段 | 客户 12 字段、商机 2 字段 | `custom/Extension/modules/<Mod>/Ext/Vardefs/` |
| **Layoutdefs（子面板）** | 在原生模块页面上挂载新模块 | 客户/商机页挂载「需求调研」「项目交接」子面板 | `.../Ext/Layoutdefs/` |
| **Language（语言包）** | 覆盖任意界面文案 | 全站中文化 + 原生语言包英文残留修复 | `.../Ext/Language/` |
| **Logic Hooks（逻辑钩子）** | 在数据生命周期插入业务逻辑 | 成交自动建交接单、概率联动 | `.../Ext/LogicHooks/` + `custom/modules/` |
| **Viewdefs（视图布局）** | 重排表单/详情页字段分组 | 4 个模块的编辑页与详情页重排 | `custom/modules/<Mod>/metadata/` |
| **自定义 View（视图）** | 完全自研页面 | 模块 4 销售看板（526 行） | `<Module>/views/view.list.php` |
| **ACL 动作注册** | 让新模块进入权限体系 | 3 个新模块各 8 个标准动作 | `acl_actions` 表 |
| **模块注册表** | 让新模块出现在导航与系统中 | 3 个新模块注册 | `custom/Extension/application/Ext/Include/` |

**关键方法论**：所有扩展走 `custom/` 目录 → 由 Quick Repair and Rebuild 合并 → **核心目录一个字节都不改**。
这意味着上游发布安全补丁时，直接覆盖核心目录即可升级，定制内容自动保留。

## 三、解决的核心问题

### 3.1 业务问题：AI 解决方案销售为什么"通用 CRM 装不下"

| # | 业务痛点 | 具体表现 | 后果 |
|---|---|---|---|
| P1 | **销售周期长、阶段多** | B 端 AI 项目成交周期 3–6 个月，需经历调研、方案、演示、谈判 | 通用 6 段流程无法反映真实进度，预测失真 |
| P2 | **决策链复杂** | 需同时跟踪决策人、预算、竞品、风险 | 信息散落在个人文档，无法沉淀 |
| P3 | **售前与销售割裂** | 售前调研结论只在邮件里，销售看不到 | 方案与承诺脱节，重复调研 |
| P4 | **销售与交付断层** ⭐ | 成交后靠人工口头/邮件交接，信息大量丢失 | **交付返工、客户预期落差、验收纠纷** |
| P5 | **过程不可视** | 管理层看不到管道健康度、输单归因 | 无法做资源调配与策略调整 |
| P6 | **客户画像粗糙** | 通用字段无法体现 AI 行业的采购特征 | 方案匹配度低，转化率上不去 |

### 3.2 问题 → 方案 → 效果

| 痛点 | 解决方案（本项目） | 落地模块 | 效果 |
|---|---|---|---|
| P1 | 重构为 **7 段式销售阶段** + 概率自动联动 | 模块 2 | 阶段贴合真实销售动作，预测可按阶段加权 |
| P2 | 需求调研模块承载 **决策人 / 预算 / 竞品 / 风险** | 模块 3 | 关键信息结构化沉淀，可检索可复用 |
| P3 | 需求调研**双向关联**客户与商机，双向可见 | 模块 3 | 销售与售前共享同一份事实 |
| P4 ⭐ | **成交即自动生成项目交接单**（逻辑钩子） | 模块 5 | 交接信息 100% 继承，零遗漏，零人工 |
| P5 | **6 KPI + 5 张图** 的一页式经营看板 | 模块 4 | 管道健康度、输单归因一目了然 |
| P6 | **12 个客户画像字段**（等级/价值/痛点/预算/周期） | 模块 1 | 方案匹配与资源投入有据可依 |

### 3.3 工程问题：技术上真正难在哪

| # | 工程挑战 | 为什么难 | 本项目的解法 |
|---|---|---|---|
| E1 | **改得动、又不改坏** | SuiteCRM 核心 20 万行代码，直接改会污染升级路径 | 建立"扩展 vs 核心"的硬边界，用 `git diff` 可验证零核心改动 |
| E2 | **保留英文 Key 但界面全中文** | `Closed Won`/`Closed Lost` 被硬编码在搜索条件、列表视图、Dashlet 数据源等多处 | **只中文化显示标签，不动内部 Key** |
| E3 | **视图布局是"完整替换"而非"合并"** | `custom/modules/*/metadata/*defs.php` 一旦存在就整体覆盖，且含运行时函数调用，无法用代码生成 | 采用**文本片段精确插入**的方式生成 |
| E4 | **自动化必须幂等** | 商机反复保存会重复建单，产生脏数据 | **按商机 ID 查重 + 运行标志位防重入**双重保护 |
| E5 | **统计口径正确性** | 漏斗按"当前停留"统计会出现后期阶段倒挂 | 改为**累计到达口径**，符合标准漏斗语义 |
| E6 | **缓存导致的"改了没生效"** | 语言包缓存、扩展合并产物、视图缓存多层 | 建立"清缓存 → 重建扩展 → 重载注册表"的固化修复流程 |
| E7 | **中文语言包质量缺陷** | 官方 zh_CN 包存在大量英文残留（Accounts 42 处、Opportunities 15 处、Home 29 处） | 以语言扩展方式逐项覆盖，未改核心语言文件 |

> 这 7 项工程挑战的完整根因分析与代码级解决记录，见 [`系统设计文档.md`](系统设计文档.md) 第 12 章。

## 五、主要应用场景

### 场景 1：一条新客户线索进来（客户画像建立）

> **人物**：销售代表小李
> **时机**：展会上拿到一家制造业企业的名片
>
> 小李在系统里建客户，顺手填上：企业规模（大型）、企业类型（民企）、所属行业（制造业）、
> 客户等级（B）、潜在价值（80 万）、当前痛点（"客服人力成本高、响应慢"）、
> 使用系统（"某国产工单系统"）、预算范围（50–100 万）、决策周期（3 个月）、
> 销售负责人 / 售前负责人。
>
> **系统支撑**：模块 1 —— 12 个客户画像字段按 4 个面板分组，录入时按业务逻辑组织，不杂乱。
> **价值**：这条客户一进来就带上了"值不值得投入、该怎么推"的判断依据。

### 场景 2：商机从接触到成交的推进（销售流程管理）

> **人物**：销售代表小李 → 销售经理
> **时机**：客户有初步意向，商机建立
>
> 商机走 **7 段式阶段**：初步接触 → 需求调研 → 方案设计 → 产品演示 → 商务谈判 → 成交 / 输单。
> 每推进一个阶段，**成交概率自动联动更新**；如果输单，必须选择输单原因（价格 / 功能不匹配 / 竞品 / 预算取消 / 决策延期）。
>
> **系统支撑**：模块 2 —— 产品类型字段 + 阶段重构 + 概率联动 + 输单归因。
> **价值**：销售经理的预测不再是"拍脑袋"，而是按阶段加权的可解释数字；输单原因沉淀成产品改进依据。

### 场景 3：售前顾问做需求调研（售前工作台）

> **人物**：售前顾问小王
> **时机**：客户同意做需求诊断
>
> 小王填写需求调研单：客户背景、业务痛点、现有系统、功能需求、技术需求、期望解决方案、
> 预算金额、关键决策人、竞争方案、风险事项、期望上线时间，并把调研单**同时关联到客户和商机**。
>
> **系统支撑**：模块 3 —— 13 个字段 + 双向关联。
> **价值**：调研结论从"邮件里的几段话"变成**结构化档案**；销售打开商机就能看到售前结论，
> 交付接手后也能回溯"当初答应过什么"。

### 场景 4：成交瞬间（⭐ 最能体现自动化价值的场景）

> **人物**：销售代表小李 → 交付负责人
> **时机**：客户签约，小李把商机阶段改为"成交"
>
> **就在保存的那一刻**，系统自动完成三件事：
> 1. 生成一张**项目交接单**（编号 `HT-2026-0007`），自动继承客户、产品类型、合同金额、币种、负责人；
> 2. 建立"客户 ↔ 交接单""商机 ↔ 交接单"的关系记录，保证 360° 视图可追溯；
> 3. 向交接负责人**派发一条"项目交接准备"待办**。
>
> 如果小李不小心又保存了一次？**不会重复生成** —— 钩子会按商机 ID 查到已有交接单，只做补全。
>
> **系统支撑**：模块 5 —— 逻辑钩子 + 幂等 + 防重入。
> **价值**：**这是整个项目最能打动面试官的一个点**。它把"人工 30 分钟、经常漏项"的交接动作，
> 变成"零人工、零遗漏、可追溯"的自动化流程。

### 场景 5：管理层做经营复盘（数据看板）

> **人物**：销售总监
> **时机**：季度经营会
>
> 打开**销售分析看板**一页看完：
> - **6 项 KPI**：客户总数 20、商机总数 30、预计销售金额、成交金额、整体成交率、平均成交周期；
> - **5 张图**：销售漏斗、产品销售金额、行业客户分布、输单原因分析、销售阶段分布。
>
> **系统支撑**：模块 4 —— 自研视图 + 本地 ECharts。
> **价值**：管道健康度可视，输单归因可量化，为"下一季度资源往哪投"提供数据依据。

### 5.6 场景 → 模块 → 能力 映射表

| 场景 | 触发角色 | 涉及模块 | 体现的产品/技术能力 |
|---|---|---|---|
| 客户画像建立 | 销售 | 模块 1 | 字段体系设计、业务分组 |
| 商机流程推进 | 销售 / 经理 | 模块 2 | 流程重构、状态机、统计口径 |

### 7.1 技术亮点（5 条，按"含金量"排序）

#### 亮点 1｜在 20 年历史的开源企业系统上做零侵入二次开发 ⭐⭐⭐

- **做什么**：基于 SuiteCRM 7.15.2 完成 5 大模块业务定制，改动 127 个文件，**核心源码零改动**。
- **难在哪**：企业级开源系统核心代码庞大，直接修改会导致后续无法升级。
- **怎么做**：严格划分"扩展层 vs 核心层"，全部通过 `custom/` 下的 Vardefs / Layoutdefs / Language / LogicHooks 机制实现，并用 `git diff` 建立可验证的边界。
- **成果**：上游发布安全补丁时可整目录覆盖升级，定制内容自动保留。

> **简历表述**：基于 SuiteCRM 7.15.2 完成 5 大业务模块的零侵入二次开发，改动 127 个文件、核心源码零改动，保障系统可平滑升级（经 git diff 全量验证）。

#### 亮点 2｜设计并落地"成交→交付"业务自动化闭环 ⭐⭐⭐

- **做什么**：商机成交瞬间，逻辑钩子自动生成项目交接单 + 建立关联 + 派发待办。
- **难在哪**：商机会被反复保存，直接建单会产生重复脏数据。
- **怎么做**：`after_save` 钩子 + **按商机 ID 幂等查重** + **运行标志位防重入**双重保护；配套 7 项自动化验收断言（可重复执行、自动回滚）。
- **成果**：交接动作从"人工 30 分钟且经常漏项"变为"零人工、零遗漏、可追溯"。

> **简历表述**：设计并实现"商机成交自动生成项目交接单"业务自动化，内置幂等与防重入保护，通过 7 项自动化验收；将人工交接从 30 分钟降至 0，杜绝信息遗漏。

#### 亮点 3｜自研数据看板与指标口径设计 ⭐⭐

- **做什么**：自研 `AID_SalesAnalytics` 模块，6 项核心 KPI + 5 张 ECharts 图表。
- **难在哪**：漏斗统计口径若按"当前停留阶段"计算，会出现后期阶段数量倒挂的错误结论。
- **怎么做**：改为**累计到达口径**（进入该阶段及之后所有阶段的商机总和），并逐项与数据库核对；ECharts 本地化部署，无外网依赖。
- **成果**：看板数字与库表 100% 一致（20 客户 / 30 商机 / 成交率 20% / 平均成交周期 85.8 天）。

> **简历表述**：自研销售分析看板（自定义视图 526 行），定义 6 项核心指标口径并实现 5 张 ECharts 图表；修正漏斗为累计到达口径，消除阶段倒挂，看板数据与库表 100% 一致。

#### 亮点 4｜重构销售流程并保持与系统内部逻辑兼容 ⭐⭐

- **做什么**：把通用 6 段销售流程重构为贴合 AI 解决方案销售的 7 段流程。
- **难在哪**：SuiteCRM 把 `Closed Won` / `Closed Lost` 硬编码在搜索条件、列表视图、Dashlet 数据源等多处；贸然改 Key 会让统计全面失效。
- **怎么做**：**只中文化显示标签，内部 Key 一律不动**；其余阶段复用原生 Key 保证兼容性最佳。
- **成果**：界面全中文的同时，漏斗、预测、关闭状态判定全部正常。

> **简历表述**：重构销售阶段为 7 段式流程并实现成交概率自动联动；识别出系统内部状态 Key 被多处硬编码的约束，通过"只改显示标签、不动内部 Key"的方案实现全站中文化且统计逻辑零损伤。

#### 亮点 5｜建立可复现的部署、验收与文档体系 ⭐⭐

- **做什么**：12 个 CLI 脚本覆盖环境初始化、数据生成、双重验收、自动化截图。
- **难在哪**：企业软件交付的失败点往往是"能跑但不可复现、无验收标准"。
- **怎么做**：Docker + 本地便携栈双轨部署；`repair → register-modules → apply-locale → seed-demo → prepare-targets` 五步脚本链；96 项定制验收 + 7 项自动化验收 + 14 页冒烟 + 14 张自动截图。
- **成果**：从空环境到可演示系统 30 分钟内完成；9 份交付文档（PRD / 功能规划说明书 / 系统设计文档 / 二次开发说明 / 测试报告 / 项目全景与技术亮点 / 简历项目描述 / 仓库结构说明 / 仓库文件清单）。

> **简历表述**：建立 Docker + 本地便携双轨部署方案与 12 个自动化脚本工具链，实现"部署→数据→验收→截图"全流程可复现；输出 9 份交付文档，定制验收 96/96、自动化验收 7/7 通过。

### 7.4 面试可能被追问的技术问题 + 应答要点

| 可能的问题 | 应答要点 |
|---|---|
| **"为什么基于开源改，不自己开发？"** | 企业软件的价值在业务贴合度，不在重复造轮子。SuiteCRM 提供成熟的权限、模块、多语言框架，我只在业务差异处自研，交付周期从数月压缩到数周。 |
| **"不修改核心代码怎么做到？"** | SuiteCRM 提供官方扩展机制（Vardefs / Layoutdefs / Language / LogicHooks / Viewdefs），全部落在 `custom/` 目录，由修复工具合并生效。我用 `git diff` 验证过：127 个应用层定制文件全部在扩展路径内。 |
| **"自动化怎么保证不出脏数据？"** | 双重保护：① 按商机 ID 幂等查重，已有交接单不重复创建；② 运行标志位防重入。并写了 7 项验收断言，包括"重复保存只产生 1 条交接单"这条。 |
| **"漏斗数据准不准？"** | 一开始不准——按"当前停留阶段"统计会出现后期阶段倒挂。我改成累计到达口径，并逐项与数据库核对。现在是 28→24→18→13→9→6，符合标准漏斗语义。 |
| **"遇到过最难的问题是什么？"** | 详情页布局空白那个。排查发现是视图布局的 `tabDefs` 所有面板 `newTab=false`，导致 tab 容器为空、所有面板被 `display:none`。这类问题页面不报错，只能从渲染结果反推。 |
| **"怎么保证交付质量？"** | 三层验收：96 项定制断言 + 7 项自动化断言 + 14 页 HTTP 冒烟，全部脚本化可重复执行。加上 14 张自动截图做视觉确认。不靠"看着没问题"。 |
| **"这个项目你自己做了哪些决策？"** | 比如保留英文销售阶段 Key 只改显示标签、漏斗改累计口径、成交自动化加幂等、砍掉"自己开发 CRM"的原始设想改为二次开发。每条决策背后都有具体的权衡。 |

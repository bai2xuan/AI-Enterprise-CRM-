# AI Enterprise CRM —— 产品需求文档（PRD）

| 项 | 内容 |
|---|---|
| 产品名称 | AI Enterprise CRM —— 企业AI解决方案销售管理平台 |
| 版本 | v1.0 |
| 形态 | 基于开源 SuiteCRM 7.15.2 二次开发的企业内部系统 |
| 模拟客户 | 智联AI科技有限公司（AI 解决方案提供商） |
| 目标用户 | 销售经理、售前顾问、交付经理、销售管理者 |
| 文档定位 | 说明"为谁解决什么问题、做成什么样、怎么衡量做成了" |

---

## 一、业务背景

### 1.1 客户是谁

**智联AI科技有限公司**是一家 To B 的 AI 解决方案提供商，向制造业、金融、医疗、政府、互联网等行业的
中大型企业客户销售四类产品：

| 产品 | 客户价值 | 典型客单价 |
|---|---|---|
| AI 知识库系统 | 沉淀企业知识资产，降低查找与培训成本 | 25 ~ 90 万 |
| 企业智能客服 | 7×24 智能应答，降低人工客服成本 | 20 ~ 170 万 |
| AI 办公助手 | 文档处理 / 会议纪要 / 流程提效 | 15 ~ 45 万 |
| 数据智能分析平台 | 多源数据接入与经营分析 | 30 ~ 120 万 |

### 1.2 业务特征（决定了 CRM 该怎么改）

| 特征 | 对系统的要求 |
|---|---|
| 客单价高、销售周期长（平均 3~6 个月） | 需要清晰的阶段划分与阶段停留时长分析 |
| 决策链复杂（业务部门 + 信息中心 + 采购 + 高层） | 需要记录关键决策人、决策周期、预算范围 |
| 售前投入重（需求调研、POC、方案设计） | 需要结构化的需求调研模块，不能只靠聊天记录 |
| 交付即口碑（AI 项目失败率高） | 成交到交付的交接必须无损、可追溯 |
| 客户画像差异大（制造业重知识沉淀、金融重合规） | 需要行业化的客户画像字段与行业维度分析 |

### 1.3 现状与痛点

| 角色 | 现状痛点 | 业务影响 |
|---|---|---|
| 销售经理 | 客户信息散落在 Excel、微信、邮件；商机阶段靠口头同步 | 销售预测不准，管理者无法判断管道健康度 |
| 售前顾问 | 需求调研无固定模板，调研结论沉淀在个人手里 | 方案反复返工，人一走需求就断档 |
| 交付经理 | 成交后才知道要交付什么，销售承诺与合同范围对不上 | 交付超期、客户满意度下降、验收扯皮 |
| 销售管理者 | 每月手工拉数据做报表，口径不统一 | 决策滞后，看不清"卡在哪一阶段、为什么输单" |

**一句话概括**：现有通用 CRM 无法承载 AI 解决方案销售特有的**客户画像、阶段化流程、售前协同、交付衔接**。

## 二、产品目标

### 2.1 业务目标

| # | 目标 | 衡量指标（系统内可观测） |
|---|---|---|
| G1 | 客户信息资产化 | 客户画像字段完整率 ≥ 80% |
| G2 | 销售流程标准化 | 100% 商机使用 7 段标准阶段；每阶段有明确"下一步行动" |
| G3 | 售前需求可沉淀 | 每条商机可关联需求调研记录，需求结论可复用 |
| G4 | 销售到交付无损衔接 | 成交商机 100% 自动生成交接单 |
| G5 | 经营分析自助化 | 管理者打开看板即可看到管道金额、阶段结构、输单归因 |

### 2.2 非目标（明确不做）

- 不做 AI 算法本身（本项目是**承载 AI 业务销售的 CRM**，不是 AI 产品）
- 不重写 CRM 内核（权限、工作流、审计、REST API 全部复用 SuiteCRM 原生能力）
- 不做移动端 App、不做计费与发票

## 三、用户角色与场景

### 3.1 角色定义

| 角色 | 系统账号 | 核心诉求 | 高频动作 |
|---|---|---|---|
| 销售经理 | `admin`（显示名：张浩然） | 快速判断商机该做什么、下一步是什么 | 新建客户/商机、更新阶段、记录跟进 |
| 售前顾问 | `lisiyuan`（李思远） | 结构化沉淀客户需求与竞争态势 | 填写需求调研、输出方案要点 |
| 交付经理 | `wangxuefeng`（王雪峰） | 接手前知道交付边界与风险 | 查看交接单、确认实施范围 |
| 销售管理者 | （复用 admin，管理视角） | 看清管道健康度与输单原因 | 打开销售分析看板 |

### 3.2 端到端主流程（LTC：Lead to Cash）

```
线索获取        需求确认          方案验证          商务谈判          签约成交          交付启动
   │               │                 │                 │                 │                 │
Accounts ───> Opportunities ───> CReq_CustomerRequirements ───> Opportunities ───> Hand_ProjectHandovers
             初步接触            需求调研/方案设计          产品演示           商务谈判          待交接→实施中→已上线
```

**关键设计判断（体现产品思维）**：

1. **成交不是流程终点**。多数 CRM 把"Closed Won"当作流程结束，但 AI 项目的口碑来自交付，
   因此本项目把"成交"设计成**交接的触发器**，而不是终点。
2. **需求调研独立成模块**，而不是塞进商机的备注字段。
   理由：一条商机的需求会演进（一期/二期），且需求要能被多个方案复用，必须有独立主数据。
3. **阶段 Key 保留英文**。SuiteCRM 内部用 `Closed Won` / `Closed Lost` 判定商机关闭状态并驱动漏斗与预测，
   中文化只能改**显示标签**，不能改 Key，否则统计口径会崩。

## 四、功能需求

### 4.1 功能一：客户生命周期管理（扩展 Accounts）

**用户故事**
> 作为销售经理，我希望新建客户时就能一次性录入企业规模、行业、客户等级、预算范围等信息，
> 以便我判断这个客户值不值得投入售前资源。

| 需求编号 | 需求描述 | 优先级 |
|---|---|---|
| F1-1 | 客户页面按"企业基础信息 / 客户价值 / 业务与需求信息 / 负责人"分组展示 | P0 |
| F1-2 | 企业基础信息：所属行业（9 类）、公司规模（5 档）、企业类型（5 类） | P0 |
| F1-3 | 客户价值：客户等级（A/B/C/D）、客户来源（7 类）、潜在价值（货币） | P0 |
| F1-4 | 业务与需求信息：当前痛点（长文本）、使用系统、预算范围、决策周期 | P0 |
| F1-5 | 负责人：销售负责人、售前负责人（均关联用户） | P1 |
| F1-6 | 客户详情页可下钻查看该客户的商机、需求调研、项目交接 | P1 |

**验收标准**：新建/编辑/详情三个页面均能看到上述字段分组，数据可正常保存与回显。

---

### 4.2 功能二：AI 解决方案销售商机管理（重构 Opportunities）

**用户故事**
> 作为销售经理，我希望商机阶段能反映 AI 解决方案的真实销售过程，并且一眼看到"这一步该干什么"。

| 需求编号 | 需求描述 | 优先级 |
|---|---|---|
| F2-1 | 产品类型字段：AI 知识库系统 / 企业智能客服 / AI 办公助手 / 数据智能分析平台 | P0 |
| F2-2 | 销售阶段重构为 7 段：初步接触 → 需求调研 → 方案设计 → 产品演示 → 商务谈判 → 成交 / 输单 | P0 |
| F2-3 | 每段阶段对应默认成交概率（10 / 25 / 40 / 55 / 75 / 100 / 0） | P0 |
| F2-4 | "下一步行动"字段（复用原生 `next_step`），必填语义 | P0 |
| F2-5 | 输单原因字段：8 类标准原因，用于输单归因分析 | P0 |
| F2-6 | 列表视图展示 客户名称 / 销售阶段 / 金额 / 截止日期 / 负责人 / 创建日期 | P1 |

**验收标准**：阶段下拉为 7 项中文标签；`Closed Won` / `Closed Lost` 的 Key 未被修改；
漏斗与预测统计结果正常。

### 4.3 功能三：客户需求调研模块（新增 `CReq_CustomerRequirements`）

**用户故事**
> 作为售前顾问，我希望有一套固定模板记录客户背景、痛点、功能需求、技术需求、风险与竞争方案，
> 这样即使我休假，同事也能接上。

| 需求编号 | 需求描述 | 优先级 |
|---|---|---|
| F3-1 | 新模块可关联客户与商机，一个客户/商机可有多条需求记录 | P0 |
| F3-2 | 需求编号自动生成（`REQ-2026-0001`），需求状态 5 档 | P0 |
| F3-3 | 需求优先级 3 档（高-核心诉求 / 中-重要提升 / 低-可选优化） | P1 |
| F3-4 | 结构化的需求内容：客户背景、业务痛点、现有系统、需求描述、功能需求、技术需求、期望解决方案 | P0 |
| F3-5 | 商务与决策：预算金额、期望上线时间、关键决策人、竞争方案、风险事项 | P0 |
| F3-6 | 详情页按 5 个面板分页签展示，长文本可读 | P1 |

**验收标准**：模块出现在顶部导航；可新建/编辑/查看；客户与商机下钻子面板可见需求记录。

### 4.4 功能四：销售漏斗分析看板（新增 `AID_SalesAnalytics`）

**用户故事**
> 作为销售管理者，我希望打开一个页面就能看清管道金额、阶段结构、产品结构、行业结构与输单归因，
> 而不是让运营同事手工做月报。

| 需求编号 | 需求描述 | 优先级 |
|---|---|---|
| F4-1 | 6 个核心指标卡：客户总数 / 商机总数 / 在途预计金额 / 已成交金额 / 商机成交率 / 平均成交周期 | P0 |
| F4-2 | 销售漏斗（**累计口径**，含阶段转化率） | P0 |
| F4-3 | 各阶段商机数量（柱）+ 金额（折线，双 Y 轴） | P0 |
| F4-4 | 产品销售金额（横向条形图） | P1 |
| F4-5 | 客户行业分布（环形图） | P1 |
| F4-6 | 输单原因分析（横向条形图，Tooltip 带出涉及金额） | P1 |
| F4-7 | 无外网依赖（图表库本地化），打开即可用 | P0 |

**指标口径定义（必须统一，否则数字对不上）**

| 指标 | 口径 |
|---|---|
| 客户总数 | `accounts` 未删除记录数 |
| 商机总数 | `opportunities` 未删除记录数 |
| 在途预计金额 | `SUM(amount)`，阶段 ∉ {成交, 输单} |
| 已成交金额 | `SUM(amount)`，阶段 = 成交 |
| 商机成交率 | 成交数 ÷（成交数 + 输单数） |
| 平均成交周期 | `AVG(DATE(date_closed) − DATE(date_entered))`，仅统计成交商机 |
| 漏斗阶段值 | **累计口径**：进入该阶段及后续阶段的商机数（不含已输单） |

**验收标准**：看板数值与直接查库结果一致；图表可交互（Tooltip / 图例）；窄屏不溢出。

---

### 4.5 功能五：销售到交付流程（新增 `Hand_ProjectHandovers`）

**用户故事**
> 作为交付经理，我希望商机一成交就自动收到一张交接单，上面带着客户、产品、合同金额和项目目标，
> 我不需要再去问销售"这单到底承诺了什么"。

| 需求编号 | 需求描述 | 优先级 |
|---|---|---|
| F5-1 | 商机阶段变为「成交」→ **自动生成项目交接单**，预填客户、商机、产品类型、合同金额、货币、负责人 | P0 |
| F5-2 | 同时**自动派发**一条"项目交接准备"待办给销售负责人（3 日内完成） | P1 |
| F5-3 | 交接单号自动生成 `HT-2026-0001`；交接状态 5 档（待交接/已交接/实施中/已上线/已验收） | P0 |
| F5-4 | 结构化交付信息：项目目标、客户需求、承诺功能、合同范围、实施周期、风险事项、验收标准 | P0 |
| F5-5 | 交付负责人字段（关联用户），明确责任到人 | P0 |
| F5-6 | **幂等保证**：同一商机重复保存不会产生重复交接单 | P0 |

**验收标准**：`scripts/verify/verify-automation.php` 全部通过（含幂等性验证）。

## 五、非功能需求

| 类别 | 要求 | 落地情况 |
|---|---|---|
| 可运行性 | 本地一键起服务即可演示 | PHP 8.3 内置服务器 + MariaDB 10.11，端口 8080 / 3307 |
| 可移植性 | 提供 Docker 部署方案 | `deploy/docker/`（Dockerfile + compose + 静默安装） |
| 可维护性 | 不修改 SuiteCRM 核心代码 | 全部改动位于 `crm/custom/` 与新增模块目录 |
| 可升级性 | 升级 SuiteCRM 不丢定制 | 依赖官方扩展机制（Vardefs / Layoutdefs / LogicHooks / 语言包） |
| 本地化 | 全站简体中文，日期 `YYYY-MM-DD`，货币 ¥ | `config_override.php` + 语言包扩展 + 用户偏好 |
| 无外网依赖 | 离线可用 | ECharts 本地化、无 CDN、无外部 API |
| 数据安全 | 密码不入库入仓 | 密码存于 `data/.pw`（已 gitignore），脚本读取变量 |

## 六、数据需求

| 对象 | 数量 | 分布要求 |
|---|---|---|
| 客户 | 20 | 9 大行业、5 类企业类型、4 档客户等级 |
| 联系人 | 12 | 覆盖决策人 / 技术负责人 / 业务负责人角色 |
| 商机 | 30 | 7 段阶段全覆盖（成交 6 / 输单 2 / 在途 22） |
| 需求调研 | 20 | 关联客户与商机，覆盖 4 类产品 |
| 项目交接单 | 6 | 与 6 个成交商机 1:1 对应 |
| 跟进记录 | 50 + 6 | 50 条销售跟进 + 6 条自动化派发的交接待办 |

**数据可信度要求**：金额与产品线区间匹配；成交商机的 `date_entered` 按阶段回填，
使"平均成交周期 85.8 天""成交转化率 21.4%"等指标具备业务解释力。

## 七、业务价值与衡量

| 价值 | 改进前 | 改进后 |
|---|---|---|
| 客户信息完整度 | 分散在 Excel / 微信，无统一口径 | 20 家客户 11 项画像字段结构化沉淀 |
| 销售过程可见性 | 靠口头同步阶段 | 7 段标准阶段 + 阶段停留时长 + 金额结构 |

| 成交→交付衔接 | 口头交接，范围扯皮 | 100% 自动生成交接单 + 待办，责任到人 |
| 经营分析成本 | 每月手工做表（约 0.5 人日） | 打开看板即得，实时数据 |
| 输单归因 | 无记录 | 8 类标准原因 + 涉及金额可视化 |

## 九、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 改动 SuiteCRM 核心导致无法升级 | 后续维护成本失控 | 强制"只进 custom/ 与新增模块"，验收脚本校验文件位置 |
| 销售阶段 Key 被中文化 | 漏斗、预测统计失效 | 保留英文 Key，仅改显示标签；`verify-customizations.php` 断言 |
| 扩展缓存不刷新导致界面显示 `LBL_XXX` | 演示翻车 | `repair.php` 显式清理模块语言缓存 |
| 演示数据不可信（日期、金额随意） | 面试时经不起追问 | 按阶段回填 `date_entered`，脚本内置口径自检 |
| 自动化产生重复单据 | 数据污染 | 逻辑钩子做幂等 + 防重入，独立验收脚本覆盖 |
